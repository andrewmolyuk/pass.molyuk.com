# Secret Relay — техническое задание для реализации

## Что строим

Однократный обмен секретом по ссылке + отдельно переданный PIN. Семейный инструмент,
не публичный сервис. Угроза, от которой защищаемся — случайная пересылка ссылки не туда
или доступ с общего устройства, а не таргетированная атака. Прототип и обоснование схемы
уже проверены в браузерном демо (см. приложенный HTML) — здесь нужна реальная реализация
с настоящим backend вместо `Map` в памяти вкладки.

## Ключевой принцип

Сервер — zero-knowledge. Он хранит только шифротекст и никогда не видит:
- сам секрет в открытом виде
- ключ шифрования
- PIN

## Стек (предложение, не жёсткое требование)

- Backend: Node.js + Express (или Fastify), либо любой стек, который удобнее Claude Code
- Хранилище: Redis (естественный TTL через `EXPIRE`, атомарный `GETDEL` для burn-after-read)
  либо SQLite, если Redis разворачивать не хочется — тогда TTL и одноразовость проверять
  вручную в транзакции
- Frontend: одна статическая HTML-страница с Web Crypto API (без фреймворков — задача
  простая, не нужен React). Можно взять за основу логику из прототипа `secret-relay-family.html`
- Деплой: планируется как self-hosted для семьи — Docker Compose (app + redis), без внешних
  зависимостей от облачных провайдеров

## Криптосхема (уже спроектирована, реализовать как есть)

1. Клиент генерирует случайный `fragmentKey` (24 байта) — уходит только в URL fragment
   (`#key=...`), сервер его никогда не получает
2. Клиент генерирует случайный PIN (6 цифр) через `crypto.getRandomValues`
3. Ключ шифрования = `PBKDF2(fragmentKey + PIN, random salt, 210000 итераций, SHA-256)` → AES-256-GCM
4. Секрет шифруется в браузере, на сервер уходит только: `ciphertext`, `iv`, `salt`, `ttl`
5. Получатель переходит по ссылке → вводит PIN (сообщён по отдельному каналу) →
   расшифровка происходит локально в браузере получателя
6. Если PIN неверный — AEAD-проверка (GCM tag) проваливается сама, никакой отдельной
   серверной проверки "правильный/неправильный PIN" быть не должно

## Модель данных

```
secret:{id}
  ciphertext   bytes (base64)
  iv           bytes (base64), 12 байт
  salt         bytes (base64), 16 байт
  created_at   timestamp
  expires_at   timestamp
  attempts     int, default 0
  max_attempts int, default 5
```

`id` — криптографически случайный, минимум 128 бит энтропии, генерируется сервером
при создании записи (не клиентом — иначе клиент мог бы влиять на предсказуемость).

## API

### `POST /api/secrets`
Тело: `{ ciphertext, iv, salt, ttl_seconds }`
Ответ: `{ id }`
Сервер сам генерирует `id`, ставит `expires_at = now + ttl_seconds`, кладёт в Redis с
нативным TTL (`SET ... EX ttl_seconds`) — так протухшие записи не нужно чистить вручную.

### `GET /api/secrets/:id`
Возвращает `{ ciphertext, iv, salt }`, если запись существует и не протухла.
**Не удаляет запись** — просто отдаёт данные для попытки расшифровки на клиенте.
404, если записи нет (протухла или уже сожжена).

### `POST /api/secrets/:id/burn`
Вызывается клиентом **после успешной локальной расшифровки** — удаляет запись.
Также инкрементирует `attempts` при вызове с флагом неудачи (см. ниже) — либо
сделать отдельный эндпоинт `POST /api/secrets/:id/attempt-failed`, который
инкрементирует счётчик и удаляет запись при достижении `max_attempts`.

**Важно (уязвимость к race condition):** между `GET` и `burn` может быть окно, где
два параллельных запроса оба успешно прочитают один и тот же секрет до удаления.
Если это критично — рассмотреть `GETDEL`-подобный паттерн: секрет отдаётся один раз,
но тогда клиент не может локально проверить PIN до "сжигания" записи (проверка PIN —
чисто клиентская операция через AEAD). Приемлемый компромисс для семейного
использования: разрешить `GET` многократно до истечения TTL или до явного `burn`,
но это ослабляет строгую одноразовость. **Решение, которое нужно явно принять в
реализации** — не оставлять как есть без выбора.

## Требования безопасности к серверу

- Только HTTPS (в проде — за reverse proxy с TLS, например Caddy/nginx)
- Заголовки ответа: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`
- CSP на странице просмотра секрета: запрет любых внешних скриптов/шрифтов
  (чтобы XSS не мог утащить `fragmentKey` из URL fragment через JS)
- Rate limit на `POST /api/secrets/:id/attempt-failed` по IP (например, 20/минуту),
  отдельно от лимита в 5 попыток на саму запись — это защита от перебора по многим
  ссылкам сразу, а не от перебора PIN на одной ссылке
- Не логировать `id` секретов вместе с IP получателя в постоянные логи, если это
  вообще логируется — либо явно предупредить в UI, что доступ логируется
- Секрет и PIN никогда не должны попасть в query string (только body запроса
  и URL fragment, которые не уходят в серверные логи веб-сервера)

## Frontend — что перенести из прототипа

Файл `secret-relay-family.html` (прилагается) уже содержит рабочую клиентскую крипто-логику:
`deriveKey()`, генерацию `fragmentKey`/PIN, шифрование/расшифровку через
`crypto.subtle`. Нужно:
1. Разделить на две отдельные страницы/роута: `/create` и `/s/:id`
2. Заменить локальный `Map` (эмуляцию сервера) на реальные вызовы к API выше
3. На странице `/s/:id` — не автоматически расшифровывать при загрузке (боты/превьюшеры
   мессенджеров иначе "сожгут" секрет раньше получателя) — только по явному клику
   "Показать секрет" после ввода PIN

## Приёмочные критерии

- [ ] Секрет и PIN никогда не появляются в сетевых запросах в открытом виде
      (проверить через DevTools → Network при ручном тесте)
- [ ] После успешного просмотра повторный переход по той же ссылке → "запись не найдена"
- [ ] После истечения TTL → "запись не найдена" даже если PIN верный
- [ ] После 5 неверных попыток PIN → запись удаляется, дальнейшие попытки бессмысленны
- [ ] Неверный PIN и "запись не найдена" не должны визуально различаться настолько,
      чтобы дать атакующему лишнюю информацию (не обязательно identичный текст,
      но не должно быть, например, разного времени ответа сервера — timing attack)
- [ ] Просмотр страницы `/s/:id` со стороны мессенджер-бота (например, отправить ссылку
      в Telegram/Slack себе и проверить, не показывает ли превью) не сжигает запись

## Что осталось решить перед реализацией (не додумывать самостоятельно, спросить у меня)

- Redis или SQLite — зависит от того, куда это будет задеплоено
- Домен/поддомен для семейного инстанса
- Нужна ли история "кто когда создавал секреты" для самого владельца (это уже не
  zero-knowledge про сам секрет, но метаданные о факте создания — отдельный вопрос
  приватности внутри семьи)
